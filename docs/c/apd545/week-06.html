1. 📑 강의 슬라이드: Week 6 · Segment 1. Automatic Resizing using Layouts #

🧭 먼저 한국어로 · 👀 읽고 이해하기 (타이핑 안 해도 돼요)

Week 4~5에서는 relocate(x, y)로 픽셀을 일일이 계산했죠. 이번엔 창 크기가 바뀌어도 알아서 배치되는 레이아웃 Pane 다섯 가지를 배워요.

이 챕터 구성

  • 👀 Why layout panes?: 레이아웃 Pane의 장점 3개: (1) 위치, 크기 계산 안 해도 됨, (2) 창 크기가 바뀌면 자동으로 다시 배치, (3) 어떤 OS에서도 깔끔.
  • ⌨️ FlowPane: (⌨️ 버튼 6개를 FlowPane에 넣고 창 너비를 줄여서 다음 줄로 wrap 되는지 확인 (HBox로 바꿔서 차이도 보기))
  • 👀 HBox / VBox: HBox는 가로 한 줄, VBox는 세로 한 줄.
  • ⌨️ BorderPane: (⌨️ center에 TextArea, bottom에 버튼 FlowPane, right에 VBox 버튼을 넣고 창 크기를 바꿔 보기)
  • 👀 Simple GridPane: 바둑판. add(컴포넌트, col, row) column이 먼저(Quiz 4 Q6).
  • ⌨️ More Complicated GridPane: (⌨️ TextField, Add, ListView, Remove를 2x2 GridPane으로 배치하고 창을 키우면 ListView만 커지는지 확인)

원문 출처: APD545 Week 6 · Segment 1 "Automatic Resizing using Layouts" 강의 슬라이드 (Mahboob Ali, Seneca) 핵심 문장 발췌

📑 Why layout panes? #

JavaFX provides a mechanism called a Layout Pane that allows the automatic arrangement of the components as the window is resized. Why? We would not have to compute locations and sizes; our components will resize automatically; our interface will appear "nicely" on all platforms. We will discuss FlowPane, BorderPane, HBox, VBox, and GridPane.

🇰🇷 한글 해설

레이아웃 Pane의 장점 3개: (1) 위치, 크기 계산 안 해도 됨, (2) 창 크기가 바뀌면 자동으로 다시 배치, (3) 어떤 OS에서도 깔끔. 그냥 Pane은 레이아웃이 없는(절대 좌표) 컨테이너예요.

📑 FlowPane #

Components are arranged horizontally from left to right, like lines of words in a paragraph. If no space remains on the current line, components flow (or wrap around) to the next "line". The height of each line is the maximum height of any component on that line.

⌨️ 이 코드는 IntelliJ에서 직접 쳐 보세요: 버튼 6개를 FlowPane에 넣고 창 너비를 줄여서 다음 줄로 wrap 되는지 확인 (HBox로 바꿔서 차이도 보기)

FlowPane aPane = new FlowPane();
aPane.getChildren().add(new Button("one"));
aPane.getChildren().add(new Button("two"));
aPane.getChildren().add(new Button("three"));
aPane.setVgap(10);                              // gap between rows
aPane.setHgap(30);                              // gap between columns
aPane.setPadding(new Insets(20, 10, 30, 40));   // top, right, bottom, left
aPane.setPadding(new Insets(25));               // same on all 4 sides

🇰🇷 한글 해설

글 쓰듯이 왼쪽 → 오른쪽, 자리가 없으면 다음 줄(wrap). 창이 좁아지면 줄 수가 늘어요. Quiz 4 Q4 정답이 FlowPane이었어요.

간격 세 가지: setHgap(옆 간격), setVgap(줄 간격), setPadding(바깥 여백).

Insets 순서: top, right, bottom, left (시계 방향). new Insets(25)는 네 방향 모두 25. Quiz 4 Q5 함정이에요.

📑 HBox / VBox #

Similar to the FlowPane in that it arranges components one after another, either horizontally or vertically. It does not have a wrap-around effect. Any components that do not fit on the line are simply not shown.

HBox aPane = new HBox();
aPane.setPadding(new Insets(10));
aPane.setSpacing(5);

🇰🇷 한글 해설

HBox는 가로 한 줄, VBox는 세로 한 줄. FlowPane과 달리 wrap이 없어서 넘치는 컴포넌트는 그냥 잘려요. 간격은 setSpacing(5) 하나(FlowPane의 hgap/vgap과 이름이 달라요). new VBox(10, a, b, c)처럼 생성자에 간격과 자식을 한 번에 넣을 수도 있어요.

📑 BorderPane #

Places components at one of five anchored positions (top, left, bottom, right or center). As the window resizes, components stay "anchored" and grow accordingly. You may place at most one component in each of the 5 positions, but this one component may be a container such as another Pane.

⌨️ 이 코드는 IntelliJ에서 직접 쳐 보세요: center에 TextArea, bottom에 버튼 FlowPane, right에 VBox 버튼을 넣고 창 크기를 바꿔 보기

BorderPane aPane = new BorderPane();
aPane.setPadding(new Insets(10));

FlowPane buttonPane = new FlowPane();
buttonPane.setHgap(10);
buttonPane.getChildren().addAll(new Button("Add"), new Button("Remove"), new Button("Edit"));

aPane.setBottom(buttonPane);
aPane.setCenter(new TextArea());

TextField statusField = new TextField("This is like a status pane");
BorderPane.setMargin(statusField, new Insets(10, 0, 0, 0));

🇰🇷 한글 해설

동서남북 + 가운데 5칸. 창이 커지면 center가 남는 공간을 다 차지하고, top/bottom은 가로로, left/right는 세로로 늘어요.

한 칸에는 하나만. 버튼 여러 개를 bottom에 두려면 FlowPane(또는 HBox)으로 묶어서 그 Pane 하나를 setBottom. Week 7 "같은 틀, 가운데만 교체"(setCenter)도 이 Pane이에요.

BorderPane.setMargin(node, insets): 특정 칸의 바깥 여백. 슬라이드는 aPane.setMargin(...)으로 썼는데 static 메서드라 클래스 이름으로 부르는 게 정석이에요.

📑 Simple GridPane #

Excellent for arranging a 2-dimensional grid of components. Components are added by specifying their column and row: aGridPane.add(aComponent, col, row);. JAVA determines the number of rows and columns from the add() calls. setHgap(), setVgap(), setPadding().

GridPane aPane = new GridPane();
aPane.setPadding(new Insets(10));
aPane.setHgap(1);
aPane.setVgap(1);
for (int row = 1; row <= 6; row++)
    for (int col = 1; col <= 8; col++) {
        Button b = new Button();
        b.setPrefWidth(200);
        b.setPrefHeight(200);
        aPane.add(b, col, row);
    }

🇰🇷 한글 해설

바둑판. add(컴포넌트, col, row) column이 먼저(Quiz 4 Q6). 행, 열 개수는 add한 값들 보고 자동으로 정해져요.

버튼을 200x200으로 "크게" 요청해도 창이 작으면 줄어들어 칸에 맞춰져요. pref는 "원하는" 크기일 뿐이에요.

📑 More Complicated GridPane #

Imagine lines between components to form a grid, number the columns and rows starting at 0 at the top left. A component can span multiple rows and columns.

⌨️ 이 코드는 IntelliJ에서 직접 쳐 보세요: TextField, Add, ListView, Remove를 2x2 GridPane으로 배치하고 창을 키우면 ListView만 커지는지 확인

GridPane aPane = new GridPane();
aPane.setPadding(new Insets(10));

TextField newItemField = new TextField();
newItemField.setMinHeight(30);
aPane.add(newItemField, 0, 0);
GridPane.setMargin(newItemField, new Insets(0, 0, 10, 0));

Button addButton = new Button("Add");
addButton.setMinSize(100, 30);
aPane.add(addButton, 1, 0);
GridPane.setMargin(addButton, new Insets(0, 0, 10, 10));

ListView<String> fruitList = new ListView<>();
fruitList.setPrefWidth(Integer.MAX_VALUE);   // take all the extra space
fruitList.setPrefHeight(Integer.MAX_VALUE);
aPane.add(fruitList, 0, 1);

Button removeButton = new Button("Remove");
removeButton.setMinSize(100, 30);
aPane.add(removeButton, 1, 1);
GridPane.setMargin(removeButton, new Insets(0, 0, 0, 10));
GridPane.setValignment(removeButton, VPos.TOP);

🇰🇷 한글 해설

복잡한 화면 그리는 순서:

  1. 종이에 컴포넌트를 그리고 가상의 선을 그어 행, 열 번호(0부터) 매기기
  2. add(node, col, row)로 배치. 여러 칸 차지는 add(node, col, row, colSpan, rowSpan)
  3. 정렬: GridPane.setValignment(removeButton, VPos.TOP) (기본은 세로 가운데)
  4. 크기 고정: setMinWidth/MinHeight로 버튼 크기 통일
  5. 늘어날 녀석 지정: setPrefWidth(Integer.MAX_VALUE)로 "최대한 커져" → ListView가 남는 공간 차지
  6. 간격: GridPane.setMargin(node, new Insets(...))

Week 4 Grocery 샘플 FXML의 ColumnConstraints, GridPane.columnIndex가 이걸 FXML로 쓴 거예요.

🧭 먼저 한국어로 · 👀 읽고 이해하기 (타이핑 안 해도 돼요)

창 위쪽 메뉴바, 오른쪽 클릭 팝업 메뉴, 체크/라디오 메뉴 항목을 만들어요.

  • 👀 Working with Menus: 구조: MenuBar ⊃ Menu ⊃ MenuItem.

  • 👀 MenuItems, separator and accelerators: accelerator: 메뉴를 열지 않고 바로 실행하는 단축키 (Ctrl+N).
  • 👀 RadioMenuItem and ToggleGroup: ToggleGroup = "이 중에 하나만" 묶음.
  • 👀 Cascaded menu and CheckMenuItem: 하위 메뉴(cascade) = Menu 안에 Menu를 MenuItem처럼 add.
  • ⌨️ ContextMenu: (⌨️ Pane을 오른쪽 클릭했을 때만 Help, Inspect 팝업이 뜨게 만들기)
  • 👀 Menu event handlers: 메뉴 항목 이벤트도 버튼처럼 setOnAction.

원문 출처: APD545 Week 6 · Segment 2 "Working with Menus" 강의 슬라이드 (Mahboob Ali, Seneca) 핵심 문장 발췌

📑 Working with Menus #

A menu is a list of commands presented to the user at his/her request. Menus can be attached to a menu bar at the top of an application or they may be pop-up menus. Classes: MenuBar, Menu, ContextMenu, MenuItem, CheckMenuItem, SeparatorMenuItem, RadioMenuItem.

🇰🇷 한글 해설

구조: MenuBar ⊃ Menu ⊃ MenuItem. MenuItem의 친척들:

  • SeparatorMenuItem: 구분선
  • CheckMenuItem: 체크 켜기/끄기 (여러 개 독립)
  • RadioMenuItem: 여럿 중 하나만 (ToggleGroup 필요)
  • ContextMenu: 오른쪽 클릭 팝업

📑 MenuBar and Menus #

⌨️ 이 코드는 IntelliJ에서 직접 쳐 보세요: File, Edit, Settings 메뉴를 만들고 단축키, 구분선, 라디오, 체크, 하위 메뉴를 다 넣어 보기

VBox aPane = new VBox();
Menu fileMenu = new Menu("_File");
Menu editMenu = new Menu("_Edit");
Menu settingsMenu = new Menu("_Settings");

MenuBar menuBar = new MenuBar();
menuBar.getMenus().addAll(fileMenu, editMenu, settingsMenu);
aPane.getChildren().add(menuBar);

🇰🇷 한글 해설

"_File"의 밑줄(_)은 mnemonic: Alt+F로 메뉴를 열 수 있어요. MenuBar는 getMenus(), Menu는 getItems()로 추가해요. MenuBar도 Node라서 VBox 맨 위(또는 BorderPane top)에 넣어요.

📑 MenuItems, separator and accelerators #

MenuItem newItem = new MenuItem("New");
MenuItem openItem = new MenuItem("Open...");
MenuItem closeItem = new MenuItem("Close");
fileMenu.getItems().addAll(newItem, new SeparatorMenuItem(), openItem, closeItem);

newItem.setAccelerator(KeyCombination.keyCombination("Ctrl+N"));
openItem.setAccelerator(KeyCombination.keyCombination("Ctrl+O"));
closeItem.setDisable(true);

Accelerators are "quick key" presses that allow the user to select the menu item without having to go through the menus.

🇰🇷 한글 해설

  • accelerator: 메뉴를 열지 않고 바로 실행하는 단축키 (Ctrl+N). mnemonic(_File)은 메뉴를 여는 키, accelerator는 항목을 바로 실행하는 키.
  • setDisable(true): 지금은 못 고르는 항목(예: 아무것도 안 열었을 때 Close).

슬라이드는 Close에 Ctrl+C를 줬는데, 보통 Ctrl+C는 복사라 실제 앱에서는 피하는 게 좋아요.

📑 RadioMenuItem and ToggleGroup #

Each RadioMenuItem is added to a ToggleGroup, to ensure that only one can be selected at a time.

ToggleGroup settingGroup = new ToggleGroup();
RadioMenuItem smallItem = new RadioMenuItem("Small");
smallItem.setToggleGroup(settingGroup);
RadioMenuItem largeItem = new RadioMenuItem("Large");
largeItem.setToggleGroup(settingGroup);
settingsMenu.getItems().addAll(smallItem, largeItem);

🇰🇷 한글 해설

ToggleGroup = "이 중에 하나만" 묶음. 각 RadioMenuItem에 setToggleGroup(group)을 해야 해요. 안 하면 Radio처럼 생겼는데 여러 개가 동시에 선택돼요. (RadioButton도 똑같아요.)

📑 Cascaded menu and CheckMenuItem #

Menu searchMenu = new Menu("Search");
searchMenu.getItems().addAll(new MenuItem("Find"), new MenuItem("Replace"));
CheckMenuItem gridItem = new CheckMenuItem("Use GridLines");

📑 ContextMenu #

A menu that will pop up wherever we right click. It is created like any other menu. However, it is not added to anything. We use the show() method in a mouse handler.

⌨️ 이 코드는 IntelliJ에서 직접 쳐 보세요: Pane을 오른쪽 클릭했을 때만 Help, Inspect 팝업이 뜨게 만들기

ContextMenu popupMenu = new ContextMenu();
popupMenu.getItems().addAll(new MenuItem("Help"), new MenuItem("Inspect"));

aPane.setOnMouseClicked(new EventHandler<MouseEvent>() {
    public void handle(MouseEvent e) {
        if (e.getButton() == MouseButton.SECONDARY)
            popupMenu.show(aPane, e.getScreenX() - 50, e.getScreenY() - 25);
    }
});

🇰🇷 한글 해설

ContextMenu는 어디에도 add하지 않아요(Quiz 4 Q7). 마우스 핸들러에서:

  • e.getButton() == MouseButton.SECONDARY: 오른쪽 버튼인지 확인 (PRIMARY는 왼쪽)
  • popupMenu.show(aPane, e.getScreenX(), e.getScreenY()): 화면(screen) 좌표에 띄우기. getX()는 노드 기준 좌표라 다른 값이에요.

간단히 하려면 컨트롤에 setContextMenu(popupMenu)를 쓰는 방법도 있어요(Control만 가능, Pane은 안 됨).

📑 setResultConverter #

If we created the dialog box elsewhere, we would not be able to access the username and password fields directly. We would need to adjust the return value of the Dialog box. If CANCEL was pressed, or the window was closed, the result will be null.

⌨️ 이 코드는 IntelliJ에서 직접 쳐 보세요: Login Dialog를 만들고 setResultConverter로 Pair를 돌려받아 출력, Cancel이면 아무것도 출력 안 되는지 확인

dialog.setResultConverter(new Callback<ButtonType, Pair<String, String>>() {
    public Pair<String, String> call(ButtonType b) {
        if (b == loginButtonType)
            return new Pair<>(username.getText(), password.getText());
        return null;
    }
});

Optional<Pair<String, String>> result = dialog.showAndWait();
if (result.isPresent())
    System.out.println("Username = " + result.get().getKey() + ", Password = " + result.get().getValue());

🇰🇷 한글 해설

왜 필요한가(Quiz 4 Q14): 대화상자를 다른 클래스에서 만들면, 호출하는 쪽은 그 안의 username TextField를 볼 수 없어요. 그래서 대화상자가 닫힐 때 돌려줄 값을 정해 두는 거예요.

  • 매개변수 b: 눌린 버튼
  • Login이면 new Pair<>(아이디, 비번) 반환 → Optional에 들어감
  • Cancel이나 X면 null 반환 → Optional이 비어서 isPresent() false

Callback<ButtonType, Pair<String,String>>은 "ButtonType을 받아 Pair를 돌려주는 함수"예요. 메서드가 call 하나라 람다 b -> ...로 줄여 쓸 수 있어요. Pair는 Week 3 제네릭의 <K, V> 예시, getKey(), getValue().

📑 Making My Own Dialog Boxes #

Dialog boxes have an owner which is the window that caused it to appear. When the application quits, all windows are closed; when the owner is minimized, the dialog boxes are also minimized.

The model is used as the "middle-man" between the two windows. When the dialog box is first opened, the model contents are used to populate the components. When the dialog box is closed with the OK button, the model is updated. When closed with CANCEL, the model remains unchanged. When either button is clicked, the dialog box closes. The standard "close" (X) should be treated as a cancel.

🇰🇷 한글 해설

owner: 대화상자를 띄운 창. 메인 창을 닫거나 최소화하면 대화상자도 같이.

모델이 middle-man(Quiz 4 Q13 서술형, 꼭 외우기):

  1. 열 때: 모델 값으로 컴포넌트를 채움
  2. 사용자가 수정
  3. OK: 대화상자 값으로 모델 업데이트
  4. Cancel 또는 X: 모델 변경 없음
  5. 어느 쪽이든 대화상자는 닫힘

📑 Dialog subclass #

    public MyDialog(Stage owner, String title, ...) {
        setTitle(title);
    }
}

🇰🇷 한글 해설

슬라이드는 extends Dialog(raw type)로 썼지만 Dialog<EmailBuddy>처럼 타입을 주면 showAndWait()가 Optional<EmailBuddy>로 바로 나와요.

📑 setResultConverter pattern #

The owner usually needs to know whether OK was pressed or cancelled. Return null to indicate that it was cancelled, and something else otherwise.

        if (b == okButtonType) {
            // extract data from the dialog box and return it

    }
});

🇰🇷 한글 해설

메인 창은 대화상자 안을 몰라요(몰라야 해요). 알아야 할 건 "OK였나, Cancel이었나" 하나. 그래서 OK면 결과 객체, 아니면 null을 돌려주게 약속해요. 호출하는 쪽은 Optional의 isPresent()만 보면 돼요.

📑 EmailBuddyPanel (view) #

public class EmailBuddyPanel extends GridPane {
    private EmailBuddyList model;
    private ListView<EmailBuddy> buddyList;
    private Button addButton, removeButton;
    private CheckBox hotListButton;

    public EmailBuddyPanel(EmailBuddyList m) {
        model = m;
        buddyList = new ListView<>();
        add(buddyList, 0, 0, 1, 3);           // col 0, row 0, spans 1 column, 3 rows
        addButton = new Button("Add");         add(addButton, 1, 0);
        removeButton = new Button("Remove");   add(removeButton, 1, 1);
        hotListButton = new CheckBox("Show Hot List"); add(hotListButton, 1, 2);
        update();
    }

    public void update() {
        int selectedItem = buddyList.getSelectionModel().getSelectedIndex();
        EmailBuddy[] exactList;
        if (hotListButton.isSelected()) {
            exactList = new EmailBuddy[model.getHotListSize()];
            for (int i = 0; i < model.getHotListSize(); i++) exactList[i] = model.getHotListBuddy(i);
        } else {
            exactList = new EmailBuddy[model.getSize()];
            for (int i = 0; i < model.getSize(); i++) exactList[i] = model.getBuddy(i);
        }
        buddyList.setItems(null);   // seems to be required for a proper update
        buddyList.setItems(FXCollections.observableArrayList(exactList));
        buddyList.getSelectionModel().select(selectedItem);
        removeButton.setDisable(buddyList.getSelectionModel().getSelectedIndex() < 0);
    }
}

🇰🇷 한글 해설

extends GridPane이라 생성자 안에서 바로 add(...). add(buddyList, 0, 0, 1, 3): col 0, row 0에서 1열, 3행 span. 오른쪽 버튼 3개 높이만큼 리스트가 길게.

update() 포인트:

  1. 선택 index 기억
  2. hot list 체크 여부에 따라 전체 또는 hot만 정확한 크기 배열로
  3. setItems(null) 후 다시 setItems(...): 편집으로 같은 객체의 이름만 바뀌면 ListView가 변화를 못 알아채서, 한 번 비웠다 채우는 요령
  4. 선택 복원, Remove 버튼 활성/비활성

📑 BuddyDetailsDialog #

⌨️ 이 코드는 IntelliJ에서 직접 쳐 보세요: EmailBuddy, EmailBuddyList, EmailBuddyPanel, BuddyDetailsDialog를 만들고 Add로 새 친구 추가, 더블클릭으로 편집, Cancel이면 그대로인지 확인

public class BuddyDetailsDialog extends Dialog<EmailBuddy> {
    public BuddyDetailsDialog(Stage owner, String title, EmailBuddy bud) {
        setTitle(title);
        ButtonType okButtonType = new ButtonType("OK", ButtonBar.ButtonData.OK_DONE);
        getDialogPane().getButtonTypes().addAll(okButtonType, ButtonType.CANCEL);

        TextField nameField = new TextField(bud.getName());          // populate from the model
        TextField addressField = new TextField(bud.getAddress());
        CheckBox onHotList = new CheckBox("On Hot List");
        onHotList.setSelected(bud.onHotList());
        GridPane grid = new GridPane();
        grid.add(new Label("Name:"), 0, 0);    grid.add(nameField, 1, 0);
        grid.add(new Label("Address:"), 0, 1); grid.add(addressField, 1, 1);
        grid.add(onHotList, 1, 2);
        getDialogPane().setContent(grid);

        setResultConverter(b -> {
            if (b == okButtonType) {
                bud.setName(nameField.getText());
                bud.setAddress(addressField.getText());
                bud.onHotList(onHotList.isSelected());
                return bud;
            }
            return null;
        });

        Node okButton = getDialogPane().lookupButton(okButtonType);
        okButton.setDisable(true);
        // on every key/check: okButton.setDisable(nameField empty || addressField empty);
    }
}

🇰🇷 한글 해설

  • 생성자에서 받은 bud로 TextField, CheckBox 초기값 채우기
  • setResultConverter: OK면 bud에 값을 써 넣고 bud 반환, 아니면 null. Cancel이면 bud는 손대지 않으니 모델이 그대로예요.
  • OK 버튼은 처음엔 비활성, 이름과 주소가 둘 다 있을 때만 활성. 슬라이드 원문의 조건식은 nameField...isEmpty() || addressField...isEmpty()예요(변환 과정에서 ||가 빠져 있었어요).

생각해 볼 점: Add일 때는 새 객체라 상관없지만, Edit일 때 OK를 누르면 원래 객체가 직접 바뀌어요. Workshop 3에서 복사본을 저장한 이유(Quiz 4 Q17)와 같은 이야기예요.

view.getBuddyList().setOnMousePressed(e -> {
    if (e.getClickCount() == 2) {

        if (i >= 0) {
            EmailBuddy selected = view.getHotListButton().isSelected()

            Optional<EmailBuddy> result =
                new BuddyDetailsDialog(primaryStage, "Edit Buddy Details", selected).showAndWait();
            if (result.isPresent()) view.update();
        }
    } else {
        view.update();   // single click: enable Remove
    }

🇰🇷 한글 해설

  • Add: 빈 EmailBuddy를 먼저 만들어 대화상자에 넘김 → isPresent()면 model.add + update. Cancel이면 아무것도 안 함(만든 객체는 버려짐).
  • Remove: getSelectedIndex() >= 0이면 model.remove(index) + update. (hot list 보기에서는 화면 index와 모델 index가 달라서 이 코드는 엉뚱한 사람을 지울 수 있어요. 버그 찾기 문제로 좋아요.)
  • Edit: getClickCount() == 2로 더블클릭. hot list 보기면 getHotListBuddy(i), 아니면 getBuddy(i). OK면 update만(객체는 대화상자가 이미 고쳤으니까).
  • 한 번 클릭이면 update()로 Remove 버튼 활성화.

📑 Dependency Injection #

Dependency Injection (DI) is a design pattern where objects receive their dependencies from an external source rather than creating them internally. Promotes loose coupling between classes. Makes code easier to test and maintain. Common in frameworks like Guice, Spring, and Jakarta EE.

Problem: classes often create their own dependencies → tight coupling. Solution: give (inject) dependencies from outside. Analogy: instead of a chef growing their own vegetables, the restaurant delivers them.

🇰🇷 한글 해설

DI 한 문장: 객체가 필요한 것(의존성)을 스스로 new 하지 않고 밖에서 받는다.

  • 문제: 클래스 안에서 new PlayerRepository() → 구현에 꽉 묶임(tight coupling). 바꾸려면 그 클래스를 고쳐야 함.
  • 해결: 생성자 매개변수로 받기(constructor injection). Week 5 View가 생성자로 model을 받은 게 이미 DI였어요.
  • 비유: 셰프가 채소를 직접 기르지 않고 납품받음.
  • 장점: loose coupling, 테스트 쉬움(가짜 Repository를 넣을 수 있음), 재사용.

📑 Dependency Injection in Practice #

public class AppModule extends AbstractModule {
    @Override
    protected void configure() {
        bind(PlayerRepository.class)
            .to(InMemoryPlayerRepository.class)
            .in(Singleton.class);
    }
}

Guice decides which implementation to provide. Controllers don't care how the repository is built.

🇰🇷 한글 해설

Guice 모듈 한 줄 해석: "누가 PlayerRepository(인터페이스)를 달라고 하면 InMemoryPlayerRepository(구현)를 줘라, 앱 전체에서 하나만(Singleton)."

방향 함정: bind(인터페이스).to(구현). 반대로 쓰면 틀려요(Quiz 4 Q10). Week 5 샘플은 Scopes.SINGLETON, 이 슬라이드는 Singleton.class인데 둘 다 같은 뜻이에요.

📑 Repository Pattern #

The Repository Pattern separates the logic that retrieves data from the business logic that uses the data, acting as a mediator between the domain and data mapping layers. Allows swapping between memory, database, or API without changing business code. Analogy: a library catalog, you don't search shelves yourself, you ask the catalog.

public interface PlayerRepository {
    ObservableList<Player> findAll();
    void add(Player player);
    void remove(Player player);
}

🇰🇷 한글 해설

Repository = 데이터 창구. 컨트롤러는 "선수 목록 줘", "추가해 줘"만 말하고, 그게 메모리인지 MySQL인지 파일인지 몰라요.

  • 비유: 도서관 책장을 직접 뒤지지 않고 카탈로그에 물어봄
  • 장점: 저장소를 갈아 끼워도 컨트롤러는 그대로. Week 8에서 InMemory → JDBC로 바꾸는 게 바로 이거예요.

인터페이스가 계약(무엇을 할 수 있나), 구현 클래스가 실제 데이터 관리.

📑 How do they both work together? #

Controller asks for data → via DI, gets a PlayerRepository. Repository provides data → doesn't matter if memory, DB, or file. DI + Repository = Decoupled, testable design.

🇰🇷 한글 해설

둘을 합치면: 컨트롤러는 DI로 Repository를 인터페이스 타입으로 받는다 → 실제 구현이 무엇이든 상관없다 → 테스트 때는 가짜, 실행 때는 진짜를 넣는다. "DI + Repository = Decoupled, testable design."

📑 Service Design Pattern #

Introduces a dedicated layer that encapsulates business logic and workflows, separating them from both the UI (controllers) and data access (repositories). Keeps controllers focused on UI events only.

  • Current: Controller → Repository → Data
  • Improved: Controller → Service → Repository → Data

🇰🇷 한글 해설

Repository만 있으면 컨트롤러가 repository.add()를 직접 부르면서 검증 규칙도 같이 들고 있어요(fat controller). 그 규칙을 Service로 빼요.

흐름 비교(Quiz 4 Q15 서술형):

  • 없을 때: Controller → Repository → Data
  • 있을 때: Controller → Service → Repository → Data

장점: 규칙, 검증, 작업 흐름이 Service에 모여서 컨트롤러는 UI 이벤트만, 테스트, 확장, 유지보수가 쉬움(separation of concerns). Week 3 Service Layer에 인터페이스 + DI + Repository가 붙어 "완전한 패턴"이 된 거예요.

public class ProductDialog extends Dialog<Product> {
    public ProductDialog(Stage owner, Product p) {
        initOwner(owner);
        setTitle("Edit Product");
        ButtonType ok = new ButtonType("OK", ButtonBar.ButtonData.OK_DONE);
        getDialogPane().getButtonTypes().addAll(ok, ButtonType.CANCEL);

        TextField name = new TextField(p.getName());
        TextField price = new TextField(String.valueOf(p.getPrice()));
        GridPane grid = new GridPane();
        grid.setHgap(10);
        grid.setVgap(10);
        grid.add(new Label("Name:"), 0, 0);  grid.add(name, 1, 0);
        grid.add(new Label("Price:"), 0, 1); grid.add(price, 1, 1);
        getDialogPane().setContent(grid);

        setResultConverter(b -> {
            if (b != ok) return null;
            try {
                double value = Double.parseDouble(price.getText().trim());
                p.setName(name.getText().trim());
                p.setPrice(value);
                return p;
            } catch (NumberFormatException ex) {
                return null;
            }
        });
    }
}
