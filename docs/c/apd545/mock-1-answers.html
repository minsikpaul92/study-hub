B. 짧은 서술 (모범 답안) #

B1. FXMLLoader는 기본적으로 컨트롤러를 인자 없는(no-arg) 생성자로 만들어요. 이 컨트롤러는 IPlayerRepository를 받는 생성자만 있으니 만들 수 없어요(예외). Guice에게 컨트롤러 생성을 맡기면 @Inject 생성자에 의존성을 넣어서 만들어 줘요.

loader.setControllerFactory(injector::getInstance);

채점 포인트: no-arg 생성자(1), Guice/injector가 생성하도록 위임(1), 정확한 코드 한 줄(1). 📍 Week 7 · Example from the class

B2. Decoupling(구체 구현에 의존하지 않음), Flexibility(구현 교체 쉬움), Testability(주입으로 테스트 쉬움), Maintainability(설정이 한곳, new가 흩어지지 않음). Flexibility 예: AppModule에서 bind(IPlayerRepository.class).to(InMemoryPlayerRepository.class)를 .to(JdbcPlayerRepository.class)로 한 줄만 바꾸면 컨트롤러 코드는 그대로 두고 메모리 저장에서 DB 저장으로 바뀐다. 📍 Week 7 · Why it matters?

B3. Entity: 고유한 정체성(identity)이 있어서 값이 같아도 서로 구분되는 객체. 예: 학번이 있는 Student, VIN이 있는 Car. Value object: 정체성 없이 값만으로 의미가 있고 혼자 존재하지 않으며 Entity를 설명, 보통 immutable. 예: Address, 색, Money(10, "CAD"). 📍 Week 8 · Entities, Value Objects

B5. PreparedStatement는 SQL 구조를 미리 컴파일하고, ? 자리에 들어가는 값은 드라이버가 자동으로 escape해서 데이터로만 취급해요. 그래서 값이 SQL 명령으로 해석되지 않아요. 예: 비밀번호 칸에 ' OR '1'='1을 넣으면 문자열 이어 붙이기 쿼리는 WHERE password = '' OR '1'='1'이 되어 항상 참이라 로그인되지만, PreparedStatement는 이 문자열 전체를 비밀번호 값으로 비교해서 실패해요. 📍 Week 8 · Benefits of using PreparedStatement

C5. 모범 답안:

public class AppModule extends AbstractModule {
    @Override
    protected void configure() {
        bind(IMenuRepository.class).to(InMemoryMenuRepository.class).in(Scopes.SINGLETON);
    }
}

public class MenuController {
    private final IMenuRepository repo;

    @Inject
    public MenuController(IMenuRepository repo) {
        this.repo = repo;
    }
}

// in start(Stage stage)
Injector injector = Guice.createInjector(new AppModule());
FXMLLoader loader = new FXMLLoader(getClass().getResource("menu-view.fxml"));
loader.setControllerFactory(injector::getInstance);

채점 포인트(5): extends AbstractModule + configure()(1), bind 방향과 singleton(1), @Inject 생성자(1), 생성자 타입이 인터페이스(1, 구체 클래스면 singleton 공유가 안 됨), createInjector + setControllerFactory(1). 📍 Week 7 · AppModule, PlayerOverviewController의 ⚠️ 설명
